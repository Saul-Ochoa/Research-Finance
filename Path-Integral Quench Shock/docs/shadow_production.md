## 1. Purpose

Shadow production runs the **frozen** model automatically and logs forecasts **before** outcomes
are known. Each forecast is scored once its horizon has passed. It never trades and **never
re-calibrates**.

The goal is to replace the single-event test (n = 1, L-002) with a growing sample of
forecast–outcome pairs, so that calibration (PIT, coverage) and tail behavior can be measured
honestly. Because v1.0.0 behaves as GBM at the overnight horizon (F-004), the shadow is in effect
measuring how well a **GBM with σ estimated from the regular session** forecasts overnight moves.
It is also the baseline that any v2.0.0 will be compared against.

## 4. Modes

| Mode | Trigger (ET) | Reference price | Horizon | Outcome | Status |
|---|---|---|---|---|---|
| `daily_close_overnight` | 16:05, Mon–Fri | Close of the last **clean** regular-session bar (normally 15:59) | 1050 min (frozen T) | `Open` of the first regular bar (09:30) of the next day that has data | ✅ implemented |
| `minute_intraday` | Every minute 09:30–15:00 | Last close | 60 min | Close 60 min later | Disabled; not implemented (raises an error if enabled) |

**How `generar_prediccion` behaves (`daily_close_overnight`):**

1. **Prediction date.** It is the ET date of `timestamp_utc`. On a weekend, or before
   `trigger_et` (16:05), it raises `PredictionSkipped`. That is an expected skip, not a failure.
2. **Load the day's bars.** If the CSV is missing, or the day is today and the last regular bar
   is earlier than 15:59 (data fetched intraday), it downloads from Yahoo. It saves to
   `data/raw/yahoo_1m/` unless `persist_data=False` (dry runs).
3. **Clean the session.** It keeps bars before 16:00 ET and drops bad ticks with
   `detectar_bad_ticks`. If no regular-session bars remain, it raises `PredictionSkipped`
   (holiday).
4. **Reference price.** It is the close of the last clean regular bar. Day data is used **only**
   for the reference price and data-quality metrics. The forecast distribution depends solely on
   the frozen parameters.
5. **Model.** It builds `PaolinelliArioliModel` from the frozen parameters and checks that
   `horizon_minutes` equals the frozen `T_minutes`.
6. **Summaries.** `pdf_summary` and `gbm_summary` are computed from the **exact** distribution.
   It also simulates 100,000 paths with the deterministic seed and stores the first 1,000 for
   reports.
7. **Notes.** If horizon kurtosis is below 0.01, it adds the note that v1.0.0 is equivalent to GBM
   at this horizon. If more than 5 % of regular bars are missing, it adds a data-quality note and
   logs a warning without blocking. If the reference bar is not 15:59, it notes that too (early
   close).

**Holidays and weekends.**

- If the prediction day has no session, the prediction is skipped.
- `find_realized_outcome` skips days without data (weekends, holidays) for up to 7 calendar days,
  and returns `None` while the target has not happened yet.
- The **actual** horizon in minutes is recorded in each evaluation.
- A missing ticker never fails the whole batch.

> **Friday and holiday-eve horizons: option A (D-020, resolves L-014).** The frozen horizon is
> T = 1050 min, but **Friday 16:00 → Monday 09:30 is 3,930 min** (3.7 × T), and a long weekend
> with a holiday is longer still. The shadow still predicts on those days with T = 1050. Friday
> predictions carry a note in `notes`, and each evaluation records `horizon_minutes_actual`.
> Holiday eves are identified only after the fact, from that field.

## 4a. Running the predictor: `scripts/shadow_predict.py`

```powershell
python scripts\shadow_predict.py                                    # all tickers in shadow_config.yaml
python scripts\shadow_predict.py --tickers NVDA --dry-run           # compute, write nothing
python scripts\shadow_predict.py --timestamp 2026-11-11T16:05:00-05:00 --dry-run   # replay a past day
```

| Option | Default | Meaning |
|---|---|---|
| `--mode` | `daily_close_overnight` | Mode from `shadow_config.yaml`; it must be enabled |
| `--tickers` | `tickers` in the config | Tickers to predict |
| `--dry-run` | off | Computes everything, but writes no JSONL and does not save downloaded raw data. The log file is still written, with lines tagged `[DRY-RUN]`. |
| `--timestamp` | now | Prediction time, ISO-8601 **with** UTC offset. Its ET date is the prediction date. |
| `--config`, `--params` | `config/…` | Alternative config or params file (tests) |

**Order of operations (D-021):**

1. Load the config and the frozen parameters, and verify the SHA-256.
2. **Pre-flight:** check every ticker's history for another parameter version. Any mismatch aborts
   the run before anything is written.
3. For each ticker, run `generar_prediccion` (§4), then `append_prediction`. A weekend, a holiday
   or a run before 16:05 ET is a **skip**, logged as a warning. An exception in one ticker is
   logged with its traceback, and the other tickers continue.
4. Print a summary table: ticker, status, reference price, q01/q50/q99 and `run_id`.

**Ticker statuses:** `written`, `duplicate` (the `run_id` was already logged; a re-run is a
no-op), `would_write` (dry run), `skipped` and `failed`.

**Exit codes:**

| Code | Meaning |
|---|---|
| 0 | Every ticker was written, duplicate or skipped (weekends and holidays exit 0) |
| 1 | At least one ticker failed, for example a ticker missing from the frozen params; the others were processed |
| 2 | Fatal: tampered parameters, history under other parameters, mode not enabled, invalid `--timestamp` or config. **Nothing was written.** |

**Log line format** (console and `logs/shadow_predict_YYYY-MM-DD.log`, named by the ET date):

```text
2026-11-17T03:27:19.242+00:00 | INFO    | NVDA  | 0fe12a6c-561b-53b1-8db8-00850e113ff6 | shadow_predict | [DRY-RUN] prediction for 2026-11-16: ref=156.1600 (bar 15:59), q01=-0.1162 q50=-0.0012 q99=+0.1137, bad_ticks=1, missing_bars=0
```

The timestamp is in UTC. `ticker` and `run_id` are `-` when they don't apply, and lines from
`src.data_loader` carry the ticker inside the message instead.

## 5. Records

**JSONL files are append-only.** Lines are never deleted or rewritten. Each line is flushed and
fsync'ed. One file per ticker and **prediction date**:

```
data/predictions/{TICKER}/YYYY-MM-DD.jsonl   one line per prediction (~24 KB each)
data/evaluations/{TICKER}/YYYY-MM-DD.jsonl   one line per evaluation, filed under the PREDICTION date
```

Filing evaluations under the prediction date means a forecast and its score share a file name.

**Identity and deduplication.** `run_id` is a **deterministic UUID** (version 5) computed from
`piqs|{params_version}|{params_sha256}|{ticker}|{mode}|{prediction_date}` (D-014). Re-running the
predictor for the same day produces the same `run_id`, so the logger writes it only once. There
is one prediction per (parameters, ticker, mode, day), and at most one evaluation per prediction.

**Version safety.** `assert_history_version` scans the ticker's prediction history and raises
`PARAMS_VERSION_MISMATCH` if it finds a different `params_version` or fingerprint. A new version
needs its own `paths.predictions` (§8). The evaluator rebuilds the model from the prediction's
own `params_snapshot`, not from the current YAML, and re-verifies that snapshot's fingerprint.

**Reproducibility.**

- Seed: `int(sha256(f"{ticker}|{mode}|{date}").hexdigest()[:8], 16)`.
- Summaries come from the exact Poisson–normal mixture, so they carry no Monte Carlo noise (D-015).
- Given the same parameters, the same `timestamp_utc` and the same day data, the whole prediction
  record is byte-identical. This is tested.


**Metric definitions:**

| Field | Definition |
|---|---|
| `pit_value` | CDF_model(r), from the exact mixture CDF |
| `in_50_interval` | r ∈ [q25, q75] |
| `in_90_interval` | r ∈ [q05, q95] |
| `in_99_interval` | r ∈ **[q005, q995]**, a true 99 % interval ([q01, q99] would be 98 %; D-016) |
| `prob_model`, `prob_gbm` | **Left** tail, CDF(r), as specified |
| `ratio_model_gbm` | prob_model / max(prob_gbm, 10⁻¹⁰) |
| `tail_direction`, `prob_*_tail`, `ratio_model_gbm_tail` | Tail **in the direction of the move** (right if r > median). For up-moves the left-tail probability is close to 1 and carries no information (D-017). |
| `log_score` | ln pdf_model(r), a proper scoring rule for comparing versions. `null` if the density underflows to 0. |
| `horizon_minutes_actual` | Minutes from 16:00 on the prediction date to the target bar. It equals 1050 on consecutive weekdays and is longer after weekends and holidays. |

**End-to-end verification (2026-11-16).** The event day replayed through the production path
(11-Nov 16:05 ET prediction → 12-Nov 09:30 outcome) reproduces F-004 exactly: NVDA
P = 1.121 × 10⁻³, ratio 1.010, actual horizon 1050 min; SPY ratio 1.000. See F-009.

- **Every level has the same per-ticker shape.** Daily, weekly and monthly add `series`;
  `cumulative.json` adds `as_of`, `n_days_evaluated` and, per ticker, `alerts_history`
  (`[{"date", "alert"}]`, built from the daily alerts).
- A statistic with no evaluations behind it is **`null`, never 0**. `n_pending` counts predictions
  whose outcome has not been scored yet.
- `by_horizon` splits on the evaluation's `horizon_minutes_actual`. A value equal to the frozen T
  goes to `standard_1050`; anything longer (Fridays, holiday eves) goes to `weekend_extended`
  (D-020).

**Alerts** (thresholds in `shadow_config.yaml`) are computed on `standard_1050` only:

| Alert | Fires when | Levels |
|---|---|---|
| `miss_99` | A realized return falls outside [q005, q995] | daily, weekly, monthly |
| `consecutive_misses_99_ge_3` | 3 consecutive standard-horizon misses. Daily: the streak ending that day, over the whole history. Other levels: the longest streak in the period. | all |
| `coverage_90_below_0.85` | 90 % coverage < 0.85, with ≥ `min_evaluations_for_rate_alerts` (20) evaluations | all |
| `pit_ks_above_0.15` | KS(PIT, uniform) > 0.15, with ≥ 20 evaluations | all |

The minimum sample size matters: a single PIT has a KS distance of at least 0.5, so without it the
rate alerts would fire every day.

**CSV exports** (`scripts/export_csv.py [--predictions] [--evaluations] [--date YYYY-MM-DD]`, by
default yesterday in ET and both kinds):

- Nested fields are flattened, for example `pdf_summary_q01`.
- The predictions CSV leaves out `pdf_samples` and `params_snapshot` and adds `params_sha256`.
- Floats are written at full precision. The files are overwritten on every run.

## 6. Interpreting PIT and coverage

**PIT** (probability integral transform) is $u = F_{\text{model}}(r_{\text{realized}})$.

- If the model is correctly calibrated, the values of u are **i.i.d. Uniform(0, 1)**.
- Alert: the KS distance between the empirical PIT distribution and the uniform exceeds
  `alert_pit_deviation` (0.15).

| PIT histogram shape | Diagnosis |
|---|---|
| Flat | Calibrated |
| U-shaped (mass near 0 and 1) | Forecast too narrow: σ_T too small or tails too thin. This is the expected failure mode of a GBM-like model if overnight tails are fat. |
| Hump in the middle | Forecast too wide (σ_T too large; see L-009 for SPY) |
| Mass piled up on one side | Bias (drift or a persistent directional move) |

**Coverage:** the share of realized returns that fall inside the central 50 %, 90 % and 99 %
intervals ([q25, q75], [q05, q95], [q005, q995]; fields `in_50_interval`, `in_90_interval`,
`in_99_interval`).

- The nominal values are 0.50, 0.90 and 0.99.
- Alerts:
  - 90 % coverage below `alert_coverage_90_below` (0.85);
  - `alert_consecutive_misses_99` (3) consecutive returns outside [q005, q995].

**Sample size:** with about 21 predictions per month, the 90 % coverage has a standard error of
≈ √(0.9·0.1/21) ≈ 6.5 percentage points. Expect 2–3 months before the alerts are statistically
meaningful. A return outside the 99 % interval is expected about once every 5 months (both tails
combined). Three in a row would have probability 10⁻⁶ under a calibrated model.

**Weekend horizons (D-020):** coverage and PIT must be reported **separately** for
`horizon_minutes_actual == 1050` and for longer horizons. A forecast with T = 1050 applied to a
3,930-minute weekend is too narrow by about √3.7 ≈ 1.9× under GBM scaling, so it will
over-produce misses on Mondays.

**Model/GBM ratio and log score:**

- With v1.0.0 the ratio is ≈ 1 by construction (F-004/F-005). It is logged so that a future
  v2.0.0 can be compared on the same days.
- The log score, $\log f_{\text{model}}(r)$, is the proper scoring rule to use when comparing
  versions.

## 7. Adding a new ticker

The `tickers` block of the params YAML is covered by the fingerprint. **Adding a ticker is
therefore a new parameter version.**

1. Make sure `data/raw/yahoo_1m/{TICKER}/` has the calibration window. Note that Yahoo keeps only
   about 30 days, so for v1.0.0's window the data must already be archived.
2. Run `python scripts/calibrate_params.py --version 1.1.0 --tickers NVDA SPY NEWT`. Calibration is
   deterministic, so the existing tickers get **identical** values. Verify this against
   `config/archive/params_calibrated_v1.0.0.yaml`.
3. Add the ticker to `config/shadow_config.yaml`.
4. Add a D-xxx row to `decisions.md`.
5. The existing tickers' shadow history continues: same parameters, new version number. Report
   the new ticker separately until it has its own history.

## 8. Rotating parameters: never in place

Production **never** re-calibrates. Parameter changes follow a release process:

1. Do the new research (for example v2.0.0 = overnight-gap calibration or Hawkes). Document it in
   `decisions.md` and `model_behavior.md` **first**.
2. Run `python scripts/calibrate_params.py --version 2.0.0`. The script refuses a version that is
   not strictly greater. It archives v1.0.0 to `config/archive/` and writes a new fingerprint.
3. The shadow detects the change in version or fingerprint. It **refuses to append** predictions
   from v2.0.0 to a history logged under v1.0.0 and fails with `PARAMS_VERSION_MISMATCH` until
   the new version is launched explicitly.
4. Launch v2.0.0 as a **new shadow from scratch**, with separate history and reports. Optionally,
   run v1.0.0 in parallel from its archived YAML for a head-to-head comparison on the same days,
   using the log score.
5. Editing the YAML by hand is always an error: the fingerprint check catches it, even when
   `version` was left unchanged.

**Time zone.** Task Scheduler runs in the machine's **local** time, so 16:05 ET must be converted
to local time. The US switches DST on dates that may not match the local calendar, so the offset
can change during the year. Check the trigger time in March and November, or set the machine's
time zone to Eastern Time. `shadow_predict.py` also checks the time itself: before 16:05 ET it
skips with a warning (exit 0) instead of predicting on an incomplete session.

**Creating the task.** Run this from a terminal, replacing `HH:MM` with 16:05 ET converted to
local time:

```bat
schtasks /Create /TN "PIQS Shadow Daily" ^
  /TR "\"D:\Proyectos Quants\Research-Finance\Path-Integral Quench Shock\scripts\run_shadow_daily.bat\"" ^
  /SC WEEKLY /D MON,TUE,WED,THU,FRI /ST HH:MM /F
```

Alternatively, use the GUI: Task Scheduler → *Create Task*.

- **Triggers:** Weekly, Mon–Fri, at HH:MM.
- **Actions:** Start a program, pointing to the `.bat`, with *Start in* set to the project root.
- **Settings:** enable "Run task as soon as possible after a scheduled start is missed". Use
  `shadow_backfill.py` to recover anything the scheduler missed (yfinance window ≈ 7 days at
  1-minute resolution).

**Logs:** console output plus `logs/shadow_predict_YYYY-MM-DD.log`, with structured fields
(timestamp, level, ticker, run_id, message). Exit code 1 means at least one ticker failed, and
the other tickers are still processed. Exit code 2 is fatal and writes nothing (§4a).
